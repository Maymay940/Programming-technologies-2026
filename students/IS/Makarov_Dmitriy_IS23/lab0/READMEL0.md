# Лабораторная работа №0

**Тема:** Знакомство с OpenAI API. Написание простого чат-бота.

**Цель работы:** Научиться работать с OpenAI-совместимым API, создать простого чат-бота, способного отвечать на вопросы пользователя, реализовать управление системными промптами, исследовать параметры генерации и организовать хранение истории диалога.

## 1. Настройка окружения

Для выполнения лабораторной работы использовались следующие технологии:

- Язык программирования — Python 3.12.
- Среда разработки — Visual Studio Code.
- API-провайдер — Z.AI.
- Языковая модель — `glm-4.7-flash`.
- Библиотека для обращения к API — `openai`.
- Библиотека для работы с переменными окружения — `python-dotenv`.
- База данных — SQLite.

В качестве языковой модели была выбрана `glm-4.7-flash`, предоставляемая сервисом Z.AI. Данный сервис поддерживает OpenAI-совместимый API, что позволяет использовать библиотеку `openai` для отправки запросов.

Первоначально было создано виртуальное окружение Python с помощью команды:

```bash
python -m venv venv
```

После создания окружение было активировано:

```powershell
venv\Scripts\activate
```

Затем установлены необходимые библиотеки:

```bash
pip install openai python-dotenv
```

Для сохранения списка установленных зависимостей использовалась команда:

```bash
pip freeze > requirements.txt
```

Для безопасного хранения API-ключа был создан файл `.env`, содержащий переменные окружения:

```env
ZAI_API_KEY=API_KEY
SYSTEM_PROMPT=Ты полезный ассистент. Отвечай на русском языке.
```

Реальное значение API-ключа не приводится в отчёте из соображений безопасности.

Также был предусмотрен файл `.gitignore`, исключающий передачу конфиденциальных данных и виртуального окружения в репозиторий.

## 2. Обращение к API

Для взаимодействия с языковой моделью использовалась библиотека `openai`.

Поскольку модель предоставляется сервисом Z.AI, был указан соответствующий адрес API:

```python
client = OpenAI(
    api_key=api_key,
    base_url="https://api.z.ai/api/paas/v4/"
)
```

Для отправки сообщений использовался метод `chat.completions.create()`:

```python
response = client.chat.completions.create(
    model="glm-4.7-flash",
    messages=[
        {"role": "user", "content": text}
    ]
)
```

В параметре `model` указывается идентификатор используемой модели, а в `messages` передаётся список сообщений с указанием ролей.

Ответ извлекается из объекта результата:

```python
answer = response.choices[0].message.content
```

После настройки подключения был выполнен тестовый запрос:

**Запрос пользователя:**

«Привет».

**Ответ модели:**

«Привет! Чем я могу помочь?»

Полученный ответ подтвердил успешное подключение к API Z.AI и корректную работу выбранной модели.

## 3. Реализация главного цикла

Для организации непрерывного взаимодействия пользователя с моделью был реализован главный цикл программы.

В качестве основы использовалась конструкция `while True`, которая позволяет многократно вводить сообщения и получать ответы.

Пример реализации:

```python
if __name__ == "__main__":
    print("Введите ваш вопрос (или 'exit' для выхода):")

    while True:
        question = input("Вы: ")

        if question.lower() == "exit":
            print("Завершение программы.")
            break

        answer = get_response(question, client)

        print("AI:", answer.choices[0].message.content)
```

После запуска программа ожидает ввода пользовательского сообщения, отправляет его языковой модели и выводит полученный ответ в терминал.

Для завершения работы предусмотрена команда `exit`.

В дальнейшем главный цикл был дополнен командами управления системными промптами, параметрами генерации и историей диалога.

## 4. Обработка ошибок (Troubleshooting)

В процессе разработки возникла ошибка авторизации:

```text
openai.AuthenticationError:
Error code: 401
Authentication Failed
```

Ошибка означала, что сервер Z.AI отклонял данные авторизации.

Для диагностики была проверена загрузка API-ключа из файла `.env` с помощью выражения:

```python
print("Ключ загружен:", bool(api_key))
```

Результат проверки:

```text
Ключ загружен: True
```

Это подтвердило наличие значения API-ключа в переменной окружения.

После проверки настроек подключения и данных авторизации удалось успешно выполнить тестовый запрос к модели.

Также во время экспериментов возникала ошибка:

```text
Error code: 429
code: 1305
message: The service may be temporarily overloaded,
please try again later
```

Данная ошибка указывала на временную перегрузку сервиса или ограничение доступности запросов.

После повторных обращений модель продолжала успешно отвечать.

Таким образом, в процессе выполнения лабораторной работы были рассмотрены ошибки авторизации и временной недоступности API.

### 5.2. Задание №2. Исследование параметров генерации

**Цель задания:** исследовать влияние изменения параметров генерации на ответы языковой модели.

Для эксперимента использовался параметр `temperature`, определяющий степень случайности при выборе следующих токенов во время генерации.

В программе была реализована команда `/temp`, позволяющая изменять значение параметра непосредственно во время работы чат-бота.

Пример передачи параметра в API:

```python
response = client.chat.completions.create(
    model=MODEL,
    messages=messages,
    temperature=temperature
)
```

Для эксперимента были выбраны три значения:

- `temperature = 0.1`
- `temperature = 0.5`
- `temperature = 0.9`

**Первый эксперимент**

Модели был отправлен запрос:

«Придумай название для новой IT-компании».

При `temperature=0.1` модель предложила названия Novus, Vortex, Quantum, Nexus и другие, распределив их по тематическим категориям.

При `temperature=0.5` были получены названия NovaTech, EonSoft, NextGen, FutureFlow и другие. Ответ содержал дополнительные категории и более подробную структуру.

При `temperature=0.9` сервер вернул ошибку HTTP 429, связанную с временной перегрузкой сервиса.

**Второй эксперимент**

Для более корректного сравнения был использован одинаковый запрос с очисткой истории диалога:

«Придумай 5 оригинальных названий для IT-компании. Только названия, без объяснений».

**Результаты:**

| Temperature | Ответ модели |
|---|---|
| 0.1 | Kinetix, Synapse, Qubit, Prisma, Aether |
| 0.5 | Ошибка HTTP 429, код 1305 |
| 0.9 | Nexum, Aeris, Kode, Flux, Ignis |

При низкой температуре модель предложила названия, связанные преимущественно с научной и технологической терминологией.

При высокой температуре были получены другие варианты, среди которых встречались короткие и абстрактные названия.

При значении `0.5` в повторном эксперименте возникла временная ошибка сервера. Однако в первом эксперименте это значение успешно обрабатывалось моделью.

**Анализ результатов**

В ходе экспериментов было установлено, что изменение параметра `temperature` сопровождается различиями в генерируемых ответах.

Низкая температура обычно способствует более предсказуемому выбору токенов, тогда как высокая может увеличивать разнообразие генерируемого текста.

Полученные результаты согласуются с ожидаемым поведением параметра, однако для статистически достоверного сравнения необходимо провести больше повторных запросов с одинаковыми условиями.

**Вывод по заданию №2**

Было реализовано изменение параметра `temperature` во время работы программы.

Проверена генерация ответов при различных значениях параметра. Полученные ответы различались по содержанию и характеру предложенных названий.

### 5.3. Задание №3. Реализация истории диалога

**Цель задания:** реализовать сохранение истории переписки, чтобы языковая модель могла учитывать предыдущие сообщения пользователя.

Для хранения истории использовался список `history`.

Каждое сообщение сохранялось в виде словаря с двумя полями:

- `role` — роль отправителя (`user` или `assistant`).
- `content` — текст сообщения.

Пример:

```python
history.append({
    "role": "user",
    "content": text
})

history.append({
    "role": "assistant",
    "content": answer
})
```

Для ограничения количества сохранённых сообщений использовалась операция:

```python
history = history[-6:]
```

Таким образом, после успешных запросов сохраняются шесть последних сообщений: три сообщения пользователя и три ответа ассистента.

Для просмотра истории реализована команда `/history`, а для её очистки — `/clear`.

**Проведение эксперимента**

Перед началом проверки история была очищена командой `/clear`.

Затем пользователем были отправлены следующие сообщения:

**Сообщение 1:**

«Меня зовут Дмитрий».

Модель ответила приветствием и обратилась к пользователю по имени.

**Сообщение 2:**

«Я учусь в Заполярном государственном университете».

Модель ответила на сообщение и продолжила диалог.

**Сообщение 3:**

«Как меня зовут?»

Модель ответила:

«Тебя зовут Дмитрий».

**Сообщение 4:**

«Какой университет я называл?»

Модель ответила:

«Ты назвал Заполярный государственный университет».

Данный результат подтвердил, что модель использует информацию из предыдущих сообщений диалога.

**Проверка ограничения истории**

После четырёх успешных запросов была выполнена команда:

```text
/history
```

В истории остались следующие сообщения:

| № | Роль | Содержание |
|---|---|---|
| 1 | user | Я учусь в Заполярном государственном университете |
| 2 | assistant | Ответ модели об университете |
| 3 | user | Как меня зовут? |
| 4 | assistant | Тебя зовут Дмитрий |
| 5 | user | Какой университет я называл? |
| 6 | assistant | Ответ о Заполярном государственном университете |

Первое сообщение «Меня зовут Дмитрий» и соответствующий ответ ассистента были автоматически удалены из сохранённой истории.

Таким образом, эксперимент подтвердил, что программа сохраняет три последние пары сообщений.

**Вывод по заданию №3**

В программе реализован механизм хранения истории диалога с ограничением количества сохраняемых сообщений.

Модель успешно использовала предыдущий контекст для ответа на вопросы пользователя.

Практическая проверка команды `/history` подтвердила автоматическое удаление старых сообщений и сохранение шести последних реплик.
